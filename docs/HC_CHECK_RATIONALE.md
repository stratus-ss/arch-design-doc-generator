# OpenShift Health Check — Check Rationale Runbook

_Last updated: 2026-08-13_

## Purpose

This document explains, for every check the health check report can produce, **what** it evaluates, **why** the threshold was chosen, **where** to find the raw evidence, and **how** to verify the result manually — independent of the report generator's code.

## How to Use This Document

**As a human validating a report (local files):** Pick a check ID from the report or audit JSON. Find its row below. Use the `jq` command in the **JSON Evidence** column against the raw `hc_collect` data. Compare your manual result to the report's claimed status.

**As a human validating against a live cluster:** Find the check row, then use the `oc` command in the **Live Validation** column. Compare live state to the report's claimed status — note that live data may have drifted since collection.

**As LLM context for generating recommendations:** Each row provides the structured rationale (threshold, evidence path, official reference) needed to explain *why* a check failed and what remediation aligns with Red Hat guidance. Feed the relevant section(s) as context when generating recommendation text for a given check ID.

## Relationship to the KB (`scripts/health_check/hc_report/kb/`)

This runbook documents the **rationale** behind each check's evaluation logic (thresholds, evidence, official references) — it is a reference for humans and LLMs validating a report. The **rendered report text** (recommendation, documentation links, and operational impact) comes from a separate, externally editable TOML knowledge base loaded by `kb_loader.py`, not from this file. When updating a check's recommendation or impact rating, edit the corresponding `[[checks]]` entry in `scripts/health_check/hc_report/kb/7_N_*.toml` — see the [Knowledge Base section of the README](../README.md#knowledge-base-kb-for-recommendations-and-notes). Use this runbook to verify *why* a KB recommendation is correct, not to author the recommendation text itself.

## Conventions

### Status Values

| Status | Meaning |
|--------|---------|
| `PASS` | The condition evaluated meets the recommended/required state |
| `WARNING` | The condition is suboptimal but not immediately harmful |
| `FAIL` | The condition violates a hard requirement or indicates active failure |
| `NOT_APPLICABLE` | The check does not apply (e.g., feature/product not installed) |
| `SKIPPED` | The check could not run because required data was not collected |
| `INFO` | Informational only — no PASS/FAIL judgment (e.g., SNO topology) |

### JSON Evidence Path Notation

Paths are written as `<category_dir>/<file>.json` → `.field.path`, e.g.:

```
03_base_platform/clusterversion.json → .items[0].spec.channel
```

This means: open `<hc_collect_root>/03_base_platform/clusterversion.json`, and the value is at `.items[0].spec.channel` using `jq` syntax.

### Citation Format

- `[Doc Title](URL)` — an official Red Hat / OpenShift documentation page directly supporting the threshold or recommended behavior (qualitative or quantitative)
- **Mixed** — part of the PASS/WARNING/FAIL matrix is doc-backed; another part is engineering judgment. The Reference cell states which branch is which.
- **Engineering judgment** — no specific official document sets this exact threshold or status mapping; the closest related reference is cited for context, but the number/mapping itself reflects internal best-practice convention, not a documented requirement
- Prefer `docs.redhat.com/.../latest/...` URLs when content is version-stable across supported releases

### Per-Check Table Columns

| Column | Meaning |
|--------|---------|
| Check ID | The identifier as it appears in the audit JSON (`id` field) or the pattern template for dynamic checks |
| Description | Plain-English statement of what is being evaluated |
| PASS / WARNING / FAIL / N-A conditions | The exact condition(s) that produce each status |
| JSON Evidence Path | Where to find the raw data in collected files, plus a `jq` one-liner for local validation |
| Live Validation | `oc` command to run against a live cluster with `KUBECONFIG` access |
| Official Reference | Citation per the format above |

**`doc_ref` audit JSON field:** Since 2026-08-03, checks whose native evaluation logic contradicts or promotes beyond a same-titled TSR/CCX status carry a `doc_ref` field in the audit JSON (`output/Health_Check_Report/*_HC_audit_*.json` → `checks[].doc_ref`) — a direct URL to the official documentation backing that specific status decision. It is the machine-readable counterpart to this table's **Official Reference** column for that individual check result; use it to jump straight to the citation without looking up the check ID here.

### Validation Methods

There are **two** ways to validate any check depending on your access:

#### Method A: Local file inspection (offline / must-gather / post-collection)

Use the `jq` command shown in the **JSON Evidence** column, run from the `hc_collect` results root. Use when:
- You have the `output/hc_collect/` directory on disk (from a live collection or fetched from supportshell)
- You're validating a report after the fact without cluster access
- You're working from a must-gather bundle

**Pattern:** `jq '<filter>' <category_dir>/<file>.json`

Example: `jq '.items[0].spec.channel' 03_base_platform/clusterversion.json`

#### Method B: Live cluster query

Use the `oc` command shown in the **Live Validation** column. Use when:
- You have `KUBECONFIG` access to the target cluster
- You want real-time validation (data may have changed since collection)

**Pattern:** `oc get <resource> -o jsonpath='{.<path>}'` or `oc get <resource> -o json | jq '<filter>'`

Example: `oc get clusterversion -o jsonpath='{.spec.channel}'`

#### Key differences between methods

| Aspect | Local file | Live cluster |
|--------|-----------|--------------|
| Wrapper | Most files are Kubernetes `List` objects (`.items[]`) | `oc get <res> -o json` returns a List; `oc get <res> <name> -o json` returns a single object |
| Namespace | Files contain all namespaces (collected with `-A`) | Add `-A` to `oc get` for the same scope |
| Freshness | Snapshot at collection time | Current state |
| Access | No cluster/network needed | Requires valid kubeconfig |

#### Hardware checks (special case)

Hardware checks (`7.9.hw.*`) collected via `oc debug node` (live) or `sysinfo.tgz` extraction (offline) cannot be cross-validated between methods because:
- Live: `oc debug node/<name> -- chroot /host cat /sys/class/dmi/id/product_name`
- Offline: `tar -xzf <must-gather>/nodes/<fqdn>/sysinfo.tgz sys/class/dmi/id/product_name --to-stdout`

Both produce the same data but through different access paths.

### Dynamic Expansion Notation

Some checks are generated once per resource (node, operator, subscription, MachineConfigPool). These are documented **once** using a template pattern like:

```
7.2.node.{shortname}.ready
```

where `{shortname}` is substituted per node at runtime. See the Appendix for the full list of expansion rules and counts.

## CCX / TSR Crosswalk Catalog

Source: [`tsr_ccx_crosswalk.json`](../scripts/health_check/hc_report/catalogs/tsr_ccx_crosswalk.json) (598 entries), consumed by [`parity.py`](../scripts/health_check/hc_report/parity.py) → `expand_with_parity_checks()`.

### Purpose

The evaluator modules (Sections 7.1-7.9 above) implement **deterministic, code-based** checks. The crosswalk catalog fills the gap for checks that exist in the TSR (Technical Support Report) reference structure or in the CCX (Insights/Compliance) rule taxonomy but do **not** yet have dedicated evaluator logic. `expand_with_parity_checks()` runs **after** all evaluator dispatch and appends catalog-derived rows for any `check_id`/title not already produced by an evaluator — it never removes or overrides an evaluator-produced check.

### Catalog Schema

Each of the 598 entries has these fields:

```json
{
  "check_id": "7.1.tsr.openshift_must_gather_collection",
  "category_id": "7.1",
  "category_name": "Base Platform Checks",
  "source": "tsr",
  "group": "pre",
  "title": "OpenShift Must Gather Collection",
  "status_hint": "INFO",
  "tsr_ref": "pre",
  "tags": []
}
```

| Field | Meaning |
|-------|---------|
| `check_id` | Unique ID, namespaced `{category}.tsr.{slug}` or `{category}.ccx_external.{slug}` |
| `category_id` / `category_name` | Which report section (7.1-7.9) this entry belongs to |
| `source` | `"tsr"` (573 entries) or `"ccx"` (25 entries) |
| `group` | TSR chapter grouping (`pre`, `section1`-`section7`) for `tsr` source, or `"external"`/`"internal"` for `ccx` source |
| `title` | Human-readable check title, also used for fuzzy-matching against runtime data |
| `status_hint` | The default/baseline status to use when no runtime data overrides it |
| `tsr_ref` | Cross-reference to the TSR chapter numbering (e.g. `3.10.2`) or `CCX:external`/`CCX:internal` |
| `tags` | Free-form tags (e.g. `["upgrade", "security"]`) |

### How Baseline vs. Runtime Status Is Resolved

`expand_with_parity_checks()` resolves status in this priority order, **per catalog entry**, at report-generation time:

1. **Skip if already covered.** If an evaluator already produced a `CheckResult` with the same `check_id`, the catalog entry is skipped. For `source=="tsr"`, normalized title matches are also skipped **unless** the TSR runtime authoritatively reports `FAIL` and no native same-title check already reports `FAIL`; in that exception case, the TSR FAIL still surfaces as an additional distinct row.
2. **TSR runtime override (highest priority for uncovered entries, plus the same-title FAIL exception above).** If a parsed TSR HTML JSON file was supplied (`--tsr-runtime-path`), and a row with a matching normalized title exists in it, that row's `status`/`evidence`/`tags` are used verbatim (mapped through `_STATUS_MAP`, e.g. `WARN→WARNING`, `NA→NOT_APPLICABLE`).
3. **CCX runtime override (`source=="ccx"` only).** If `12_ccx/ccx_rules.json` was collected and contains a rule matching the entry's normalized title, that rule's `status`/`message`/`tags` are used.
4. **CCX baseline status (`source=="ccx"`, `use_ccx_baseline_status=True`, no runtime match).** Falls back to the catalog's `status_hint` field, with evidence explicitly stating the check requires Red Hat Insights data and advising the user to run `insights-client` or review via `console.redhat.com/insights`. Note: `--ccx-baseline-status` defaults to **off** — without it enabled, this step is skipped and the entry falls through to step 5 (SKIPPED).
5. **Default `SKIPPED`.** If none of the above apply (typical for `source=="ccx"` entries without live data and without `--ccx-baseline-status`), the entry is emitted as `SKIPPED` with evidence directing the user to collect Insights data or provide a matching TSR HTML via `--tsr-html` or the configured TSR HTML directory.

### The `_hc_not_found` Handling for Runtime CCX Data

`12_ccx/ccx_rules.json` is treated as absent (contributing zero runtime overrides) if it is missing, or if it carries `_hc_error` or `_hc_not_found` markers — in that case, all `source=="ccx"` catalog entries fall through to step 4 (baseline) or step 5 (skipped), never silently producing a false PASS/FAIL.

### Validating CCX/TSR Parity Rows

To check whether a specific `7.x.tsr.*` or `7.x.ccx_external.*` row in a report came from the catalog fallback path vs. a genuine runtime source, inspect its evidence text: catalog-fallback rows contain phrases such as `"No TSR runtime data supplied"`, `"was not found in the supplied TSR HTML export"`, `"--ccx-baseline-status is enabled"`, or `"has no live data available"`. Genuine runtime-sourced rows do not contain these fallback phrases.

```bash
jq '.entries[] | select(.source=="ccx")' scripts/health_check/hc_report/catalogs/tsr_ccx_crosswalk.json
grep -c '"source": "ccx"' <(jq -c '.entries[]' scripts/health_check/hc_report/catalogs/tsr_ccx_crosswalk.json)
```

## Appendix — Dynamic Check Expansion Rules

The following patterns generate multiple report rows from a single evaluator code path. Understanding these is necessary to predict how many checks a given cluster will produce, and to correctly interpret "N checks" counts in the report summary.

| Pattern | Check ID Template | Count Driver | Source Section | Example (validation dataset) |
|---------|--------------------|--------------|-----------------|-------------------------------|
| Per-node | `7.2.node.{shortname}.{suffix}` where `suffix` ∈ `{ready, os, cpu, memory, disk, kubelet, sysreserved}` | `node_count × (6 or 7)` — `sysreserved` is conditional | 7.2 Topology | `worker-01` × 7 nodes = up to 301 rows across 43 nodes |
| Per-node (utilization) | `7.5.node.{shortname}.utilization` | `node_count × 1` (only if `oc adm top nodes` succeeded) | 7.5 Cluster Health | one row per node with metrics-server data |
| Per-node (hardware) | `7.9.hw.{shortname}.{suffix}` where `suffix` ∈ `{identity, cpu, memory, disk}` | `node_count × 4` (only for nodes where `oc debug` succeeded) | 7.9 Hardware | one set of 4 per node with hardware inventory collected |
| Per-node (Prometheus allocation) | `7.8.node.{shortname}.alloc` | count of distinct nodes appearing in any of 5 Prometheus vectors | 7.8 Metrics | one row per node with Prometheus data |
| Per-operator | `7.3.co.{name}` | count of entries in `cluster_operators.json → .items` (typically 30+ on OCP 4.18) | 7.3 Components | `7.3.co.authentication`, `7.3.co.baremetal`, etc. |
| Per-subscription | `7.1.sub.{name}` | count of entries in `subscriptions.json → .items` | 7.1 Base Platform | `7.1.sub.advanced-cluster-management` |
| Per-MCP | `7.2.mcp.{name}` | count of entries in `machineconfigpool.json → .items` (typically 2: `master`, `worker`, + custom pools) | 7.2 Topology | `7.2.mcp.master`, `7.2.mcp.worker` |
| Per-ingress-controller | `7.3.ingress.{name}` | count of entries in `ingresscontroller.json → .items` (typically 1: `default`, + any sharded controllers) | 7.3 Components | `7.3.ingress.default` |
| Per-product (layered) | `7.4.{product_key}` and `7.4.tsr.{safe_title}` | fixed list of 12 products (`_LAYERED_PRODUCTS`) + fixed list of TSR product groups (8 groups, each with 1-9 sub-titles) — gated by `_hc_not_found` per product | 7.4 Layered Products | most rows `NOT_APPLICABLE` unless the product is actually installed |
| Per-etcd-pod (metrics) | `7.8.etcd.wal.{pod}`, `7.8.etcd.backend.{pod}`, `7.8.etcd.db.{pod}` | count of distinct etcd pods in the Prometheus vector (typically 3) | 7.8 Metrics | one row per etcd pod for each of the 3 metrics |
| Catalog expansion (TSR/CCX) | `{category}.tsr.{slug}` / `{category}.ccx_external.{slug}` | up to 598 catalog entries, minus any already covered by evaluator output | All sections + CCX | see CCX Crosswalk Catalog section above |

**Predicting total check count for a given cluster:** `static_evaluator_checks (~180-220, varies by which N/A branches trigger) + node_count × (6-7 topology + up to 1 utilization + up to 4 hardware + up to 5 metrics) + operator_count + subscription_count + mcp_count + ingress_controller_count + (598 - covered_catalog_entries)`. For the example validation cluster (43 nodes, 30+ operators, several subscriptions, 2 MCPs), this produces well over 1,000 total rows, consistent with the report's observed scale.
